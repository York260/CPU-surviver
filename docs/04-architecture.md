# 04｜技術架構與工程守則（v0.2）

> **目標：** 系統長大之後，還能放心調整和除錯，避免「修一個錯，蹦出十個錯」。
> **做法：** 下面的分層、守則和測試，都是為了這個目標設計的。

---

## 1. 技術棧（提議，D-008 待確認）

| 層 | 選擇 | 理由 |
|---|---|---|
| 語言 | TypeScript | 邏輯層、伺服器、客戶端共用同一種語言和型別 |
| 專案結構 | npm workspaces monorepo | 各層的界線清楚，又能共用程式碼 |
| 邏輯層 | 純 TypeScript，不用任何遊戲框架 | 可以單獨測試、模擬結果可重現 |
| 伺服器 | Node.js + `ws` | 輕量、透明；通訊協定由我們自己定義，方便除錯 |
| 客戶端 | Phaser 3 + Vite | 成熟的 2D 框架，支援 Tiled 地圖、攝影機、輸入、音效 |
| 資料驗證 | zod | 內容檔格式錯誤時，載入當下就失敗，並清楚指出哪裡錯 |
| 測試 | Vitest（邏輯）、Playwright（瀏覽器冒煙測試） | 雲端環境裡兩種都能跑 |
| 規範 | ESLint，加上模組邊界規則 | 用工具強制分層，不靠人記 |
| CI | GitHub Actions | 每次 push 自動跑全部檢查 |
| 地圖 | Tiled（免費） | 你也可以自己動手改地圖 |

**為什麼不用 Godot？**
- Godot 本身很好。但在這個專案裡，主力開發者（我）在雲端環境裡比較難自動建置、測試和截圖驗證 Godot 專案。
- 朋友也得先下載安裝才能玩。

## 2. 分層

```
content/ （JSON 資料、Tiled 地圖、主題文字）
     │ 讀取（載入時驗證格式）
     ▼
packages/sim  ── 純邏輯：不認識畫面、網路，也不讀現實時間
     ▲                ▲                 ▲
     │                │                 │
packages/server   packages/client   packages/tools
（權威執行 sim）  （預測與插值、     （重播、無頭模擬、
                    畫面、輸入）       內容檢查）
```

**鐵則：**
- `sim` 不能 import `server`、`client`、Phaser、`ws`，也不能使用 DOM。
- `client` 永遠不直接修改遊戲狀態，只送出「指令」。
- 以上兩條都寫成 ESLint 規則，違反就無法通過 CI。

## 4. 邏輯層核心設計

### 4.1 輕量 ECS
- **實體：** 一個數字 ID。
- **元件：** 純資料，每種元件一張表。
- **系統：** 一個函式，事先宣告它讀哪些元件、寫哪些元件。

```ts
interface System {
  name: string;
  reads: ComponentKey[];   // 讀取的元件
  writes: ComponentKey[];  // 寫入的元件（工具會檢查有沒有寫到宣告以外的元件）
  run(world: World, ctx: TickContext): void;
}
```

- **執行順序** 由設定檔 `schedule.json` 決定，例如：

  ```
  input → movement → bugAI → combat → health → cost → discovery → spawning → dayCycle
  ```

- **每個系統都可以單獨關閉。** 出問題時，可以逐一關掉系統來二分法找出問題。
- **用標籤，不寫特例。** 實體的差異用特性標籤表達（例如 `hands`、`climb`、`sanctuaryBlocked`），系統只讀標籤，不寫「如果是某種角色就怎樣」。這樣新增角色或兵種時，只要加資料，不必修改既有系統。

### 4.2 指令和事件：唯一的出入口
- **指令（Command）：** 外部要改變遊戲狀態的**唯一**方式，例如 `{tick, playerId, kind: "move", data}`。
- **事件（Event）：** 系統通知「發生了什麼事」，例如 `BugKilled`、`AbilityUsed`、`DayEnded`。
  - 事件是模組之間的整合合約：發出者不用知道誰在聽。
  - 所有事件都寫進**事件紀錄**。群心演化（M08）、倖存報告（M20）、平衡分析都讀這同一份紀錄。

### 4.3 可重現（決定性）
- **固定 Tick：** 每秒 20 次。邏輯層只認 Tick，不讀現實時間。
- **命名亂數流：** 從局種子分出 `rng("spawning")`、`rng("abilities")` 等獨立的亂數流。
  - 在 A 模組多用一次亂數，不會改變 B 模組的結果。
  - 換句話說，加功能不會讓整個平行時空跟著位移。
- **禁止** 在 `sim` 裡使用 `Math.random`、`Date.now`，由 ESLint 規則把關。
- **因此：** 「種子 + 內容版本 + 指令紀錄」就能**完全重現**一局，這就是**重播檔**。

### 4.4 序列化
整個世界狀態都可以序列化。存檔、網路快照、測試比對都用同一套機制。

## 5. 網路模型

- **伺服器權威：** 伺服器執行 `sim`，以 20Hz 廣播快照。
- **客戶端：**
  - 其他實體：延遲約 100ms 做插值，畫面比較平滑。
  - 自己的移動：先做預測，收到伺服器結果後再修正。
- **快照分視角：** 組快照時，用 `visibleTo(實體, 觀看者)` 決定每位玩家能收到什麼。例如每位玩家的異能線索和日誌只送給本人；這也能防止作弊。這個掛鉤在 I1 就預留。
- **通訊協定：**
  - 有版本號，版本不符就拒絕連線，並顯示清楚的錯誤訊息。
  - 編碼方式抽象成介面：先用 JSON，需要時再換成二進位。

## 6. 測試金字塔

| 層級 | 測什麼 | 例子 | 抓什麼問題 |
|---|---|---|---|
| 單元測試 | 單一系統 | 代價不夠時，會觸發反噬 | 邏輯錯誤 |
| 情境測試 | 幾個系統一起運作 | 3 隻蟲包圍玩家，200 tick 之內玩家應該倒地 | 整合錯誤 |
| **黃金重播** | 整局 | 固定的重播檔跑完後，最終狀態的雜湊值不變 | **「修一個蹦十個」的警報器**：任何意料之外的連鎖改變都會被抓到 |
| 無頭模擬 | 平衡 | 機器人自動跑 1,000 局，統計存活率 | 必死的種子、數值失衡 |
| 瀏覽器冒煙測試 | 實際畫面 | 開頁、連線、截圖 | 畫面壞掉、啟動失敗 |

**黃金重播的規則：**
- 只要修改造成重播結果改變，CI 就會失敗。
- 如果改變是**預期中**的（例如調整了數值），要更新重播檔，並在提交訊息裡說明原因。

## 7. 除錯工具

| 工具 | 用途 |
|---|---|
| ` 除錯面板 | 點選實體查看所有元件；即時顯示事件流；看緊張度曲線 |
| 時間控制 | 暫停、逐格執行、×4 加速 |
| 指令台 | `spawn bug 10`、`give medkit`、`setDay 3`、`reveal ability` |
| 匯出重播 | 遇到 bug 時按一個鍵，就會存下重播檔，傳給我就能完全重現 |
| 系統開關 | 執行中關閉某個系統，用來隔離問題 |
| 內容檢查 | `npm run content:check`：驗證所有資料檔的格式 |

## 8. 工程守則

1. **單向依賴。** `sim` 不認識畫面和網路，模組只能往下依賴。
2. **模組之間只透過元件、事件、公開 API 溝通**，不碰別的模組內部。
3. **每個模組都有 README 合約：** 寫明責任、讀寫哪些元件、事件、可調參數。
4. **數值和內容都放在資料檔裡**，載入時驗證格式。
5. **所有隨機都用命名亂數流**，`sim` 內不讀現實時間。
6. **每個 bug 都要能用重播檔重現。**
7. **修 bug 前，先寫一個會失敗的測試**，確認它重現了問題，再動手修。
8. **每個系統都可以單獨開關**，用來二分法找問題。
9. **每一輪交付前，所有測試都必須通過。** 黃金重播有改變，要說明原因。
10. **小步提交，一次只改一件事。** 提交訊息要寫清楚改了什麼、為什麼。

## 9. 存檔和版本相容

- 存檔和重播檔都帶有**格式版本**和**內容版本**。
- 格式升級時，附上遷移函式，舊檔還能讀。
- MVP 階段，存檔只需要支援「點名時存檔、下次從同一天繼續」。
